# 虚拟主播切片收益与持续优化方向

记录日期：2026-10-07。项目：`D:\bilive`。

## 用户目标

通过本项目减少虚拟主播切片的人工工作，逐步形成可持续的投稿收益。用户认为当前自动切片质量偏低，愿意先尝试增加产量，同时希望持续改善质量、速度、稳定性和收益表现。本记录是开发方向，不代表系统已经能够自动盈利。

衡量产量时统计有效成片与有效投稿，不能只数候选、上传次数或成功返回的 BV 号。增加产量是否有效，需要结合投稿表现、实际结算收入、模型费用、处理时间和人工复核时间判断。

## 优先顺序与验收方向

| 优先级 | 工作 | 可检查的完成条件 |
|---|---|---|
| 1 | 话题选择与活动关联 | 搜索真实话题，展示描述和活动信息，保存所选话题，投稿时携带所需字段；不只拼接 TAG 字符串。按所选活动核对资格，区分普通话题、关联活动和确认收录。 |
| 2 | 真实成片质量诊断 | 抽取不同主播的现有成片，与原始录播比较，记录断句、铺垫缺失、重复、无有效内容、字幕错误和标题不符等问题；根据实际样本选择一项最主要问题修复，并在同批样本复验。 |
| 3 | 保留最低质量的产量优化 | 改善候选召回、内容去重和失败恢复，以每小时源录播得到的有效成片数、人工修改量衡量；只有证据支持时才调阈值或增加并发。 |
| 4 | 标题、封面、简介与 TAG | 让投稿信息对应片段内容，使用主播档案与内容特征；记录不同方案的投稿表现，不默认夸张标题或增加标签能提升收益。 |
| 5 | 投稿表现与收入反馈 | 关联片段、BV 号、话题及活动信息，读取可获得的播放/互动/观看数据；收入来自实际结算或用户核对，未知值保留未知，不用播放量推算成确认收入。 |
| 6 | 成本、速度与稳定性 | 结合现有阶段耗时定位瓶颈，记录模型调用成本、失败率和人工耗时。优先改最影响有效产量的环节，保持单机实现简单。 |

## 持续优化方法

### 下一轮待办（2026-10-07 用户要求先计划，暂缓实施）

主要优化聊天、整活与弹幕互动；唱歌片段不作为专项验证重点。

1. 聊天边界保护：检查自动字幕边界吸附是否删掉已选中的铺垫或落点。工作区使用现有 `outward_only` 的小改动已于 2026-10-08 完成离线验证：边界与分析流水线回归 32 项通过，包含隔离真实媒体的音画、时长与字幕时间检查。仅选择容差内最近的外侧边界，测试中的前后无关句子未进入字幕；真实聊天样本仍待今晚取得后复核，不能据此认定主题收尾已经解决。未部署，详见切片质量改进记录。
2. 主题收尾：选择几条已有聊天切片，人工标记标题事件的起点、落点和无关拖尾，比较模型建议。优先复用本地字幕与已有分析，不按谢礼关键词机械裁剪，不先降低质量门。若需新的付费外部样本调用，另行确定样本范围。
3. 字幕文字：以主播名、圈内梗、口语错字为重点验证已接入的轻量校正；核对原意、时间和行数保持不变。拿不准时保留原文，结果仍需人工确认。
4. 周报反馈：按既定每周日 20:00 复盘，比较同主播、相近内容和发布年龄的播放互动增量；先形成有样本支持的经验，不把低播放直接归因为切片问题，不用播放量推算收入。

第 1 项离线验证已完成，下一次用今晚取得的聊天样本复核第 1、2 项的真实内容效果。活动话题关联仍保留在收益路线中，后续按质量问题与实际活动机会调整优先级。当前不重启 Worker、不重新分析、不改写成片或投稿。

每轮围绕一个有实际样本支持的问题，保存修改前后的证据及验证结果。优先使用已有阶段耗时、主播经验和任务记录，不先搭建庞大的新评测或调度系统。完成一项后根据新数据调整下一项优先级。

本轮先保存投稿类型修复及这份路线。后续首先接入真实话题选择，再进行真实成片质量抽样。每次开发明确区分已实现、离线验证、在线只读验证和真实投稿结果。

用户表达了长期自动化收益目标，但没有指定无人审核发布规则或自动开启分析。现有人工批准和审核设置保持；以后需要调整时，围绕具体可验证的行为单独确定范围。

## 每周数据复盘（2026-10-07 已授权）

- 用户选择每周日北京时间 20:00 复盘。已创建本聊天的 Codex heartbeat 自动化「虚拟主播切片每周复盘」，状态 ACTIVE；这是应用侧定时复盘，不是录制器或上传消费者内置功能。
- 采集入口：在项目根目录运行 `.venv-win\Scripts\python.exe scripts/collect_publication_feedback.py --days 90`。只读查询已发布稿件，快照写入 `artifacts/research/publication-feedback/`；认证失败或分页不完整时停止，不保存不完整结果。
- 首份真实基线包含近 90 天的 8 条已发布稿件，读取播放、点赞、投币、收藏、分享、评论和弹幕；接口没有提供完播率、观看时长、曝光或收入，缺失值保持未知。
- 每次按 BV 号比较增量，区分新发布和积累至少 7 天的稿件；优先比较同主播、相近发布年龄与内容类型，并结合字幕、候选依据和人工反馈复核代表样本。7 天仅是观察分组，不是删除或判坏门槛。
- 经验与待验证改进保存到 `artifacts/research/weekly-reviews/` 的日期报告。每次优先一个有证据的问题；样本不足不自动推断低播放原因，不把统计数据伪装成人工正负样本。
- 自动化可修复有充分证据、不改变生产处理策略的确定性小缺陷并运行验证。模型指导、阈值、投稿策略和主播档案先形成待应用建议；不自动投稿、报名、修改历史稿件、部署、提交或推送 Git。
- 没有新增可分析稿件或可靠新结论时保持安静；有重要经验、已验证改进、失败或需要用户操作时通知。
