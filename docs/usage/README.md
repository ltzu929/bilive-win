# 使用说明

在本机双击 `启动Bilive.cmd`，打开[录播库](http://127.0.0.1:2233/workbench/#/library)。日常操作从选场次开始。首次安装或服务未就绪时，见[运行与配置](#运行与配置)。

## 审核、字幕与发布

### 从录播到候选

1. 在「直播间」管理录制房间。录制结束后 Worker 将 FLV 转封装为 MP4，校验成功后移除源 FLV。关闭工作台网页可以继续录制。
2. 在「录播库 → 切换场次 / 管理」按 UP、房间号、文件名或录制日期找场次。点「AI 分析本场录播」，系统按同名 XML 弹幕找到候选区间，再将候选送去判断。
3. 在「01 选择候选」查看片段。带 AI 编辑建议的候选可以点「看依据」，跳到模型指出的音画位置。核对上下文后保留或废弃，工作台会选中下一条未审核候选。

默认从录播库手动发起实时分析。在设置中开启「录制结束后自动 AI 切片」可让新完成的录播走实时分析，已启用夜间批量的主播优先走批量流程。在「切换场次 / 管理」可以取消排队中的实时分析或跳过本场，随后仍可手动补选和整场复核。

| 页面显示 | 可以做什么 |
|---|---|
| 未召回候选区间 | 这场没有符合弹幕条件的窗口。可从源录播手动补选。 |
| AI 返回空结果 | 模型看过的候选没有返回达标片段。展开「分析证据与占用」查看候选区间、弹幕统计和已保存的判断理由。 |
| 分析等待、暂停或失败 | 先看页面显示的阶段及原因。Worker 已停且有未完任务时点「恢复分析」。缺凭据、模型或依赖时按设置页提示处理，失败后可重试。 |

### 每晚 23:30 批量分析

1. 打开「主播档案」，选中要处理的主播，勾选「每晚 23:30 批量分析此主播录播」，点「保存档案」。开关按主播分别保存，默认关闭，适用于启用后新录完并完成转封装的场次。
2. 保持电脑和 Bilive 后台运行到北京时间 23:30。Worker 在本机准备候选视频，到点交给 MiMo 批量推理。23:30 后才录完并完成转封装的场次留到下一晚。没有录下来的内容直接跳过。
3. 在录播库查看场次。「等待 23:30 批量提交」表示候选已准备好。「等待 MiMo 批量结果」表示已进入云端等待阶段。云端已接收的任务可以在电脑关机后继续执行，下次启动 Bilive 后会检查并取回结果，完成后照常审核切片。
4. 如果显示「夜间批量分析失败」，先看页面中的原因。需要当场处理时可点「改用实时分析」。若要停止以后批量提交，回到该主播档案，取消勾选并保存。已提交的云端批次会继续取回结果。

批量折扣用于第一轮候选视频判断，使用普通按量 API Key 和账户余额。本地转写仍由 Whisper 完成。已启用的字幕轻校正，以及审核时手动重新判断候选、生成投稿文案，仍按实时方式处理。[MiMo 批量推理与计费](https://mimo.mi.com/docs/zh-CN/quick-start/usage-guide/text-generation/batch-api)

### 审核与补漏

- 调整当前片段时，用源播放器定位，在源时间轴上设置入点和出点，点「保存当前范围」。补选另一段时，先在播放器旁填好这段的源入点和出点，再点「新建补选片段」，在弹窗核对标题并点「新建人工片段」。
- 有原候选时可以「重新判断原候选」。新建议单独展示，点「将建议填入范围草稿」后仍能修改，保存范围后再核对字幕。
- 在「取舍理由（选填）」说明想保留的反应、缺少的前情或改动原因。技术故障、重复版本、发布取舍和「拿不准」都可以分别标记。保留时可一起保存，也可以单独「保存备注」。
- 模型明确给出废弃判断才可能自动清理候选素材。人工废弃会撤回这条切片尚未批准的暂存记录，理由和源录播仍可查阅。已经批准或正在处理的片段受保护。

### 字幕与成片

在「02 核对字幕」点击行号，播放器会跳到对应位置。编辑表里的时间从**所选源区间开头**算起。可改字、改时间、增删行。缺字幕时点「本地模型识别字幕」，试听返回的草稿后再保存。轻校正可以结合主播专名和短音频修正用词，保留各行时间。

字幕样式按全局默认、主播覆盖、单条切片的顺序取值。可选字幕预设，也可修改当前样式。文字和样式都改过时，按钮为「保存字幕和样式」。浏览器会暂存未提交的编辑。改范围、字幕或样式后，要重新生成当前版本成片。

在「03 确认成片」播放带字幕的成片。点「生成成片」或「重新生成成片」会把结果暂存到发布队列。聊天片段还可以逐段检查自动剪掉的空档。

### 聊天自动精剪

1. 在「02 核对字幕」保存当前版本字幕，再进入「03 确认成片」。已识别的聊天片段会自动生成**精剪预览**。人工补选或类型未知的片段可点「生成聊天精剪预览」。明确标为唱歌、跳舞、游戏实况等类型的片段走常规成片流程。
2. 在「聊天自动精剪」查看原片时长、预览时长和每段剪去的位置。检测结合字幕、人声、画面变化、声音和弹幕反应，在片头、片尾和片中寻找较长空档。
3. 点「听剪点」从接缝前试听，点「看原段」对照同一处源录播。需要留住停顿、表情或等弹幕的节奏时，点「恢复这段」。也可再点「重新剪掉」。等预览更新后继续试听。
4. 对新剪法满意，点「采用这版并生成成片」，音画与烧录字幕一起按选中的剪点缩短。想保留当前成片的剪法，点「沿用原剪法生成成片」。没有合适空档时，预览保留完整片段。

剪点列表和字幕编辑器使用所选源区间的时间。精剪播放器、生成的成片和投稿页显示剪后时长。试听或恢复剪点只更新预览，点采用才会把新剪法用于正式成片。

### 发布与主播默认

1. 在「03 确认成片」点「去投稿」，或在「发布队列」选一条待确认切片，点「编辑投稿」。
2. 填写标题、简介、分区编号、标签和可选的粉丝动态。需要文案时，在投稿页「文案助手」点「生成文案建议」。它使用已保存字幕、当前片段看点和主播指导生成标题、简介和标签。点「采用建议」后先核对，再点「保存草稿」。
3. 制作封面时，播放到主体清楚的位置，点「从当前画面选帧」。有推荐位置时也可点「看推荐画面」。选中候选缩略图，点「下载原图」与「复制 GPT 提示词」，把原尺寸 PNG 和提示词发给网页版 GPT。将做好的 JPG、PNG 或 WebP 上传到同一页，查看预览并「保存草稿」。
4. 「话题 / 活动」可按关键词搜索并选择，话题占一个标签，连同普通标签最多 10 个。「加入合集」点「读取合集」再选合集和小节。选回「不参与话题」或「不加入合集」并保存即可清空。
5. 当前版本成片就绪后，点「提交投稿」进行人工批准，在「发布队列」查看进度。只想稍后继续时点「保存草稿」。本地显示 `published` 并取得 BV 号后，审核、公开可见和活动收录情况到创作中心核对。

标题等发布默认值按全局、主播、单片段继承。「主播档案 → 默认加入合集 → 读取我的合集」适合给同一主播设置常用合集和小节。新建的自动片段和人工片段复制该项，已有片段保留原选择。单条稿件可在投稿页覆盖，工作台在保存和投稿前核对相应选项。

上传消费者在 Worker 管理下独立运行。远端已有视频标识时，重试投稿复用已上传媒体。免费合集在投稿取得 BV 后单独关联。若关联失败，在发布历史点「重试加入合集」即可重试该步骤。[投稿页实现与排查](../development/submission-editor.md)

### 主播反馈

保留、废弃、补选、改范围或文案时，工作台按房间收集人工记录，按每条片段的最新判断统计。「主播档案 → 建议与历史」可查样本与修改经过。默认至少需要 5 条有效样本，其中有保留样本，也有内容废弃、纠正或发布取舍依据。技术故障、重复和拿不准的记录单列。

条件满足后，保存新的人工反馈会刷新待应用建议，也可点「收集人工取舍并生成建议」。展开「查看片段与人工依据」核对，再点「人工应用建议」，后续分析才使用更新后的指导。历史反馈补录工具为 `scripts/sync_editorial_feedback.py`，默认预览，加 `--write` 才写入。

### 整场终审与回收

在「整场复核」处理完每条候选，所有保留片段的当前成片都已批准后，点「完成整场审核」。没有候选或还有无片段的待核对结果时，需要明确选择「确认本场无可保留内容」。已发布且本地成片已按期清理的稿件也可完成复核。

审核结果先独立保存。自动清理开启、期限已到且保护条件满足时，系统再排源包回收。要主动回收已审核的场次，可以点击源包回收区或拖入该区。「录播回收」能查看范围、逐项结果和阻塞原因。需要暂留某场素材时，在「录播回收」选中场次，点「保留此录播」。

## 运行与配置

### 安装与启动

在项目根目录准备 uv、Git、FFmpeg 和 ffprobe。两个安装脚本分别创建工作台环境 `.venv-win`（默认 Python 3.13）与录制器环境 `.venv-recorder`（默认 Python 3.10），录制器首次安装会从示例生成 `settings.toml`。

```powershell
cd D:\bilive
.\setup_windows_workbench_env.ps1
.\setup_windows_recorder_env.ps1
```

配好下表中的本机文件后，运行 `.\start_bilive.ps1` 或双击 `启动Bilive.cmd`。启动器会补齐缺失的 Dashboard、Worker、录制器。若端口属于其他服务，它会报告冲突。启动日志在 `logs/startup/`。单独启动入口分别为 `start_windows_dashboard.ps1`、`start_pipeline.ps1`、`start_windows_recorder.ps1`。

| 地址 | 用途 |
|---|---|
| `http://127.0.0.1:2233/workbench/` | 工作台日常入口，同一端口的 `/tasks` 是 blrec 原生录制管理页 |
| `http://127.0.0.1:2234/` | Dashboard 直连入口，`/api/health` 可检查服务 |
| `http://127.0.0.1:2235/health` | Worker 运行时的健康状态 |

Worker 会在提交任务时唤醒，默认空闲 900 秒后退出。手动暂停会留下 `.runtime/worker-paused` 并保留排队任务，通过工作台显式启动 Worker 可恢复处理。2233 的 `/studio-api/` 向 2234 转发工作台请求，`/api/v1/` 由录制器提供。

### 配置入口与生效

| 文件 | 用途 |
|---|---|
| `bilive-server.toml` | 入库服务模板，未设置 `BILIVE_CONFIG` 时读取 |
| `.secrets/runtime.toml` | 本机服务配置，由 `BILIVE_CONFIG` 指定 |
| `settings.toml` | blrec 房间与录制参数，模板为 `settings.example.toml` |
| `.secrets/env` | 本机环境变量，包括 `BILIVE_CONFIG`、`BLREC_API_KEY`、`MIMO_API_KEY` |
| `.secrets/bilibili.cookie` | 本机录制与投稿使用的 Cookie 文件 |

首次配置时，可将 `bilive-server.toml` 复制到 `.secrets/runtime.toml`，在 `.secrets/env` 单独一行填写 `BILIVE_CONFIG=.secrets/runtime.toml`。同一文件用 `名称=值` 设置录制器所需的 `BLREC_API_KEY` 和模型调用所需的 `MIMO_API_KEY`。B 站 Cookie 单独写入 `.secrets/bilibili.cookie`。使用默认字幕识别前，准备好本地 faster-whisper large-v3 模型目录或缓存，Worker 会在本机查找并预检。[本地模型查找](../../src/bilive/worker/preflight.py)

设置页可统一保存多个分区的草稿。自动分析、字幕样式、发布默认和清理策略由对应功能动态读取。修改模型、路径等参数后，按页面提示在任务结束后重启相应服务。支持的环境覆盖优先于配置。`.secrets/env` 只填充进程中尚未设置的变量。旧配置中的 Whisper、字幕样式和对齐参数仍可读取，显式设置的新键优先。

默认运行目录为 `Videos`、`logs`、`artifacts`、`.bilive-jobs`，上传库为 `src/db/data.db`。隔离运行可用 `BILIVE_VIDEOS_DIR`、`BILIVE_LOG_DIR`、`BILIVE_ARTIFACTS_DIR`、`BILIVE_JOBS_DIR`、`BILIVE_DB_PATH` 覆盖。Dashboard 与 Worker 应使用同一组目录。可通过 `dashboard.allowed_hosts` 或 `BILIVE_DASHBOARD_ALLOWED_HOSTS` 增加允许访问的 Host。

### 模型、性能与网络

- **视频判断与文案。** 模板使用 MiMo 实时接口，默认模型 `mimo-v2.6-flash`。候选分析、字幕轻校正和手动生成文案会调用外部服务。模型请求并发与本机分析副本的编码并发可分别配置。
- **字幕识别。** 本机使用缓存的 faster-whisper large-v3，模板为 CUDA/float16、2 个 CPU 线程，顺序解码。普通识别默认关闭 VAD，`asr_batch` 保留作旧配置兼容。主播专名用于后续校正。正式字幕优先复用已有辅助转写，需要补识别时直接从源录播提取对应区间和前后余量。Worker 在正式分析前进行本地模型预检。开启 `unload_audio_model_after_analysis` 时会在整场分析或单条识别结束后释放模型。
- **转码。** Worker 与由媒体工具入口启动的 FFmpeg 在 Windows 使用正常进程优先级。每个进程内 FFmpeg 串行执行，软件编解码与滤镜线程上限为 4。模板 `[video].encoder` 为 `h264_nvenc`，该配置下 720p 分析副本使用 CUDA 缩放和 NVENC 编码。无对应硬件时配置 `libx264`，也可通过 `BILIVE_VIDEO_ENCODER` 选择编码器。
- **网络。** 录制器、工作台、Worker 和上传进程启动时清除本进程的代理变量并设置 `NO_PROXY=*`。使用透明代理时，在代理软件中配置相应直连规则。

## 维护与开发验证

### 录播与切片保留期

本机运行配置开启自动清理，录播与成片均保留 5 天。仓库模板关闭自动清理。两者均设 `unprocessed_days=5`、`published_hours=120`、`upload.delete_after_success=false`。设置页可查看清理开关和期限，录播回收页可查各场次的具体到期时间。

| 素材 | 期限起点与处理 |
|---|---|
| 源录播 MP4、遗留 FLV 与同场关联文件 | 未处理场次按录制时间起算。无法从遗留 FLV 文件名读取录制时间时取文件修改时间。所有保留切片均已发布时，从最后一次成功发布起算。部分已发布时取原始期限与最近发布时间延长期限两者中的较晚值。到期后 Worker 把源包移入 Windows 回收站。 |
| 已发布成片 | 从成功发布时间起算，到期删除片段记录引用的 `artifacts/<segment_id>/final_output.mp4`。 |
| 未发布成片 | 从最近生成或替换成片的文件时间起算，到期删除同一成片文件。后台会检查活跃任务和上传队列，已批准等待上传或正在上传、投稿的文件受保护。 |

手动保留会保护该场次及其成片。源包回收与成片到期清理独立进行。成片清理保留字幕、封面、审核和投稿资料。需要继续验片时，可在「录播回收」标记保留。实际清理后，「冻结清单及逐项结果」记录源包处理情况。

### Windows 计划任务

从项目根目录运行以下脚本可查看安装计划，各自加 `-Install` 才注册到 `\BiliveV2\`。录制器和 Dashboard 在登录时由 `pythonw.exe` 无控制台启动。保留期检查设为每日 08:30，支持错过后补运行。

```powershell
.\install_windows_startup_tasks.ps1
.\install_windows_recording_retention_task.ps1
```

`scripts/recording_retention.py` 是实际的维护入口，执行时先清理到期成片，再检查源包并将符合条件的回收任务交给 Worker。关机期间保留期照常累计。

### 历史媒体维护

停止录制并确认 Worker、上传消费者及持久任务空闲后，可先生成历史媒体审计报告。

```powershell
.\.venv-win\Scripts\python.exe scripts/recording_history.py --report .runtime/reports/history.json --audit-mp4
```

显式加 `--execute` 才修复历史 FLV，验证 MP4 后移除对应 FLV。另加 `--delete-invalid` 才删除确认无效的文件。登记成片和上传引用路径受保护。Eagle 插件另行同步源索引书签，源视频仍存放于原目录。

### 开发验证

在项目根目录使用工作台的 Python 环境。修改剪点、字幕烧录或取帧时可先运行对应媒体回归，再运行全量用例。Windows 下用 PowerShell 展开 Node 测试文件列表。

```powershell
.\.venv-win\Scripts\python.exe -m pytest -q tests/test_chat_trim.py tests/test_finalize_pipeline.py tests/test_cover_editor.py
.\.venv-win\Scripts\python.exe -m pytest -q
node --test (Get-ChildItem tests/*.test.cjs).FullName (Get-ChildItem eagle-plugin/tests/*.test.mjs).FullName
```

投稿适配器可用 `scripts/verify_upload_adapter.py` 做隔离核对。原生双环境验收可设置 `BILIVE_NATIVE_ACCEPTANCE=1` 后运行 `tests/test_analysis_pipeline.py -k completed_recording`。这两项使用隔离材料。过去的专题验证见[历史记录](../history/README.md)。

### 投稿反馈采集

