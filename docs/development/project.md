# 项目说明

Bilive 在 Windows 本机完成直播录制、弹幕选段、字幕制作与人工审核，调用 MiMo 判断候选，通过 B 站接口投稿。从代码追一条切片，可以依次看录制完成事件、分析记录、片段版本与上传队列。本文按 2026-11-22 的实现整理。日常操作见[使用说明](../usage/README.md)，下一轮工作见[优化计划](optimization.md)。

## 工作台产品与设计约定

| 入口 | 用户在这里完成的工作 |
|---|---|
| 录播库 | 选择场次、启动分析或手动补选。在同一个播放器旁依次完成「01 选择候选」「02 核对字幕」「03 确认成片」。 |
| 直播间 | 管理录制房间、查看录制状态，异常时定位房间和任务。 |
| 发布队列 | 查看待确认、执行中、失败和已发布的投稿。从待确认切片进入独立投稿页，保存草稿或提交投稿。录播库的「去投稿」也通往这一页。 |
| 主播档案 | 维护主播的字幕样式、投稿默认值和编辑指导，查看带来源的人工取舍，决定是否应用建议。 |
| 录播回收 | 查看源录播保留期限、手动保留、终审与回收结果。 |
| 设置 | 编辑服务配置，分辨保存后即时生效和需要重启的字段，查看对应服务状态。 |

界面沿用浅冷灰背景和白色编辑区，蓝色用于主操作、选中和焦点。时间、字幕和文件名优先保证可读。选择播放器或字幕行时保持当前片段上下文，长列表独立滚动，详细证据按需展开。离开编辑区前提示未保存内容。后台任务显示阶段，版本冲突和失败保留草稿并给出可继续的操作。完整播放记录供人工核对，批准的决定由用户作出。

- 切片审核给当前步骤保留一个明确的主操作。宽屏并排显示播放器与编辑区，可切换大画面。连续取舍后定位下一条待审候选。保留和废弃都可填入理由。
- 字幕列表以正文编辑为主，点击行可定位。字幕和样式可以一起保存，恢复的浏览器草稿仍需与服务端当前版本核对。
- 发布默认值与字幕样式支持全局、主播和单片段覆盖。单条片段的编辑不会回写主播默认。模型、设备与并发参数放在高级设置。

## 进程与配置

| 组件 | 职责和入口 |
|---|---|
| 录制器 · 2233 | blrec 使用 `.venv-recorder` 录制视频与弹幕，并报告录制完成。日常入口 `/workbench/` 和同源代理 `/studio-api/` 都在这一端口。[录制器](../../src/bilive/recorder/) |
| Dashboard · 2234 | 提供静态前端与 API，校验版本、保存编辑、提交持久任务。前端为原生 JavaScript/CSS。[API](../../src/bilive/api/app.py) · [前端](../../frontend/) |
| Worker · 2235 | 使用 `.venv-win` 领取任务，完成转封装、分析、识别、取帧、精剪预览、渲染与回收。耗时任务串行执行，发布批准使用独立线程。同一片段仍需检查版本和任务占用。[任务执行器](../../src/bilive/worker/runner.py) |
| 上传消费者 | 处理已激活的 SQLite 上传行，上传媒体、投稿、重试并记录远端结果。由 Worker 管理子进程。[运行管理](../../src/bilive/worker/runtime.py) · [上传队列](../../src/bilive/upload/) |

一键启动器会识别已占用端口并补齐所需服务。日常写操作先保存动作任务，再请求唤醒 Worker。Worker 默认空闲 900 秒后退出，浏览页面只查询状态。用户暂停后，暂停标记会阻止自动唤醒，已落盘任务留待恢复。Windows 登录计划任务启动录制器和 Dashboard。Worker 与媒体子进程使用正常优先级，FFmpeg 在同一进程内串行启动，编解码和滤镜线程上限为 4。[启动器](../../start_bilive.ps1) · [唤醒逻辑](../../src/bilive/worker/control.py) · [媒体进程](../../src/bilive/media/process.py)

服务读取 `BILIVE_CONFIG` 指向的 TOML，未指定时使用仓库的 `bilive-server.toml`。本机路径及凭据放在忽略入库的配置中，blrec 单独使用 `settings.toml`。模板关闭自动分析，字幕识别使用本地 faster-whisper large-v3，视频判断与字幕轻校正使用 MiMo。模板使用 NVENC。无对应硬件的环境可显式选择 `libx264`。配置字段、支持的环境覆盖与缺省值见[配置加载器](../../src/bilive/config/settings.py)和[服务模板](../../bilive-server.toml)。

## 从录制完成到投稿

主播可单独开启夜间批量。转封装成功后登记本场并准备本地候选，Dashboard 每 30 秒检查待办，在北京时间 23:30 向 Worker 派发到点的提交任务。23:30 后才就绪的录播等次日晚间。云端等待状态按场落盘，在回填结束之前保护源材料。Worker 记录上传文件 ID、创建意图和远端批次编号，重启后按编号查询并对照候选 ID 导入结果。回填复用实时分析的去重、字幕、成片和暂存流程。[调度与恢复](../../src/bilive/analysis/nightly.py) · [批量输入与结果](../../src/bilive/analysis/batch_pipeline.py)

1. **转封装与召回。** 完成事件触发媒体验证与转封装。手动启动分析或配置为自动分析后，系统从弹幕密度召回候选区间，准备视频副本及可选的带时间辅助转写。MiMo 按候选返回片段、判断依据，还可给出看点、依据时间和推荐封面帧。工作台分别展示无召回、模型返回空结果、明确丢弃和运行失败，保留原场次的手动补选入口。[分析流水线](../../src/bilive/analysis/pipeline.py)
2. **字幕与初版成片。** 自动通过需要 `keep`、各项质量分达标并通过去重。正式字幕优先复用可用的辅助识别，需要补识别时从原录播取带前后余量的音频并对齐边界。Whisper 顺序解码。已确认专名用于后续校正。文本校正保留时间与行数。对齐后发现重复的片段留作人工复核。自动通过的片段可生成成片并暂存，人工也可编辑范围、字幕与样式后重新生成。[语音识别](../../src/bilive/vendor/autoslice/mllm_sdk/audio_analyzer.py) · [字幕校正](../../src/bilive/vendor/autoslice/transcript_correct.py)
3. **聊天自动精剪。** 有当前已保存字幕的聊天片段可在「确认成片」生成独立预览。识别空档时结合字幕、人声、突发声音、画面运动、推荐画面与互动弹幕。用户可以逐段听剪点、看原段、恢复或重新剪掉。采用时校验预览编号和片段版本，按采用的剪点生成成片。继续生成或切换预览时，原有成片仍可用。[空档识别](../../src/bilive/media/chat_trim.py) · [预览任务](../../src/bilive/media/chat_preview.py)
4. **投稿资料与封面。** 投稿页按已保存字幕、人工看点、片段音画依据和主播指导提供文案建议。选帧优先使用原录播，其次是覆盖当前区间的候选或有效成片。原图和针对该切片的提示词交给用户在 GPT 网页版制图，回传成图并保存即可采用。也可沿用默认封面。保存资料可保留有效成片，人工点击「提交投稿」后才会创建发布批准任务。[投稿页](submission-editor.md) · [封面处理](../../src/bilive/media/cover.py)
5. **积累人工反馈。** 人工保留、废弃、补选及范围或文案修改形成可追溯记录，按片段最新判断刷新该主播的待应用建议。内容选择、理解纠正与发布偏好分别处理，技术失败和清理空间的决定不作内容负例。用户应用建议后，新分析读取对应主播的正式指导。[主播反馈](../../src/bilive/lifecycle/profiles.py) · [编辑记录](../../src/bilive/media/editorial.py)

## 存储、时间坐标与版本

默认录播位于 `Videos/`。分析记录跟随源录播保存为 `*.mp4.task.json`。片段状态在 `artifacts/segments/`，可编辑字幕在 `artifacts/subtitles/`，正式成片在 `artifacts/<segment_id>/final_output.mp4`，聊天预览在 `artifacts/candidates/<task_id>/chat-preview/`。后台任务在 `.bilive-jobs/`，运行锁和服务标记在 `.runtime/`，上传队列默认位于 `src/db/data.db`。API 与 Worker 应使用同一组目录。

| 使用位置 | 时间坐标 |
|---|---|
| 录播播放器、片段范围、已保存看点依据和推荐帧 | 源录播绝对秒。封面帧文件名使用源录播的毫秒值。 |
| 模型返回的选段和依据 | 相对于候选起点。进入片段记录前加上候选起点并校验范围。 |
| 字幕编辑器、精剪建议和已采用剪点 | 相对于当前所选片段的起点，包含原段中拟剪去的空档。 |
| 精剪预览、成片播放进度与烧录字幕 | 扣除之前已剪去的时长。剪点和字幕存储继续使用原选段坐标，只在生成和播放时换算。 |

例如，片段从源录播第 100 秒开始，剪去片内 4–7 秒。源录播第 111 秒的字幕在编辑器显示为片内第 11 秒，在精剪成片中第 8 秒出现。[时间换算](../../src/bilive/media/cut_timeline.py) · [渲染](../../src/bilive/media/finalize.py)

同一片段以 `segment_id` 标识，写入携带期望的 `revision`。改变源范围会清空精剪方案、使字幕和成片失效。改字幕或样式需要重烧。新增字幕与已采用剪点重叠时，保存会移除相应剪点。工作台同时核对成片版本、字幕版本、文件和发布状态。已批准内容受到锁定，事务失败或版本冲突时从任务记录和队列状态定位。[工作台状态与锁](../../src/bilive/media/workbench.py)

动作任务按 `pending → processing → done / failed` 落盘。领取任务和重启恢复都检查锁与执行进程身份。原执行进程已退出的 `processing` 任务可重新回到 `pending`。处理状态与内容判断分别保存，例如动作已经 `done` 时，片段仍可处于待人工复核的 `review`。回收另有 `trash_status` 记录阻塞和部分移动等结果。[任务存储](../../src/bilive/jobs/action_jobs.py) · [状态定义](../../src/bilive/domain/states.py)

## 发布与回收

生成成片后，队列记录为 `staged`。首次批准通常依次进入 `queued → uploading → uploaded → publishing → published`。保有远端文件名的重试可以复用已上传媒体，避免重复传输。任务失败或取消在队列单独展示，B 站审核、公开展示和收益要到平台核对。[状态定义](../../src/bilive/domain/models.py) · [消费者](../../src/bilive/upload/consumer.py)

源录播回收和成片清理共用保留期配置，针对不同文件执行：

- **源录播。** 检查覆盖 MP4，以及未成功转封装的遗留 FLV。保留期按场次起算。所有保留片段都已投稿时，按最后一次投稿时间加 `published_hours`。部分投稿的场次也保留已发布片段的窗口。到期时核对录制、活动任务和手动保留状态，冻结清单后交给 Worker 移入 Windows 回收站并逐项记录结果。[源录播生命周期](../../src/bilive/lifecycle/review.py)
- **本地成片。** 维护任务先检查各片段的 `final_output.mp4`。已投稿的从投稿时间计，其他可清理的成片从文件修改时间计。跳过手动保留、活动任务和正在流转的队列项，到期直接删除符合条件的成片文件，保留字幕、片段记录和投稿凭据，再处理源包。[成片清理](../../src/bilive/lifecycle/clip_retention.py) · [维护入口](../../scripts/recording_retention.py)

仓库模板为 `enabled=false`、`unprocessed_days=5`、`published_hours=120`，并关闭投稿成功即删成片。缺少 `published_hours` 配置项时，代码回退到 24 小时。以正在使用的配置为准。Windows 计划任务安装器将维护检查安排在本机时间 08:30，手动终审也可从录播库独立完成。[计划任务定义](../../scripts/windows_tasks.ps1)
