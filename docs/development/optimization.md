## 虚拟主播切片收益与持续优化路线

用户方向记录于 2026-10-07；2026-10-10 整理。本文是计划，不承诺盈利，不代表待办已实施。

### 目标与衡量

减少虚拟主播切片的人工工作，尝试增加有效产量，并持续改善质量、速度、稳定性与收益。统计有效成片和有效投稿，结合实际结算、模型成本、处理耗时与人工复核时间；不只数候选、上传次数或 BV 号，不用播放量推算确认收入。

重点内容为聊天、整活与弹幕互动，唱歌不是当前专项验证重点。用户反馈质量偏低，不能预先断言根因属于某个模型、阈值或召回算法。

### 聊天切片的优先改进方向（2026-10-11 用户确认）

先改善单条切片的有效内容密度，再扩大产量。主要针对聊天、整活和弹幕互动；唱歌不作为专项。以下是已确认的改进方向，尚未实施或完成效果验证。

1. **事件结束就收尾，优先验证。** “帮狐狐找老婆”保存的字幕约在第 33 秒结束标题对应观点，片段却长约 111 秒，后续主要为谢舰长、报页数和告别；“按摩办卡”也夹入较长谢礼。两条媒体已不在原路径，当前依据是字幕和分析记录，不能据此确认视听效果或低播放原因。选段应明确指出标题事件的最后一个有效回应，以此确定结束位置；谢礼本身构成梗时保留，不按关键词机械删除。此前一次提示调整验证仍有拖尾，不能将补充提示当作问题已解决。
2. **开头让陌生观众能理解。** 新合同片段以“是有来跟我们说过的”开头，随后进入官签与合同流程，是否缺少必要前情仍需试听。检查人物、事情和必要背景能否在短开头交代清楚；不一律延长铺垫，不为了句子完整引入无关对白。
3. **标题、简介以最终成片为依据。** 合同片段标题中的“两年半”在保存的选段字幕中未找到支持，可能指签约资历而非等待时长；简介里的“光头是我妈”也未出现在现有字幕中。成片尾部仍有未独立核实的内容，因此这些是待核对线索，不能直接判错。选段完成后逐条核对标题事实和简介承诺的梗，定位到最终成片的具体秒数，避免沿用整个候选窗口的描述。

2026-10-11 用户随后确认按预期收益、修改成本与验证难度推进：先收紧标题、简介的生成依据，再小批比较 MiMo 开关思考模式，随后针对拖尾调整选段提示。事件收尾仍是重要质量方向，但不再作为第一项实施工作；MiMo ASR 替换、Batch 接入与扩大召回排后。

第一项已修改现有选段请求的提示：先确定建议区间，文案仅描述区间内有依据的内容；数字、时间、关系和引语不明确时省略，不把猜测写成事实，不为保留文案扩大选段。没有增加第二次模型调用、改变输出字段或重写既有稿件。这是提示约束，不是程序自动核实事实，也没有依据正式字幕重新生成文案。离线回归与真实模型效果分别记录，真实效果仍待同批样本比较。

首次提示修改的定向回归：`tests/test_reused_mimo_video_analyzer.py`，25 passed（4.50 秒）；验证现有 MiMo 请求、响应解析与失败处理兼容性，不证明模型遵循新增文案约束。该轮未调用真实模型或重启运行中的服务。

随后经用户授权，用 2026-10-10 呜米录播完成真实研究：原弹幕阈值 3.0 召回 0，临时在隔离研究中降到 1.5 取得 3 个窗口，另加 1 个开场探索窗口。共 24 次调用（14 次视频、10 次文本），API 返回合计 458,059 tokens，实际账单费用未查询。A–D 单次选段加文案生成仍出现标题确定化、跨段描述和复测边界漂移；固定选段后仅提供段内证据的 E/E2 在所检查的三段中更少跨段挪用，但转写噪声与标题可读性仍需整理。推荐后续评估局部的“根据当前片段生成文案”能力，不把新增生成步骤的效果全部归因于提示词。两条研究预览、比较及限制见本地 `artifacts/research/umi-prompt-20261011/REPORT.md`。生产召回/质量门、原任务、批准与上传未修改，研究提示和新增调用流程未接入生产；没有独立完整试听或普遍效果验证。

下一轮先用现有可用聊天样本对照原版与新提示生成的文案，记录选段外信息、数字/引语歧义、遗漏及人工修改量，结合音画核对，不能只凭字幕缺词认定错误。后续边界验证再人工标出必要铺垫、笑点、最后有效回应及无关收尾，记录误删、拖尾和人工接受情况。已清理媒体的旧样本只作为文字线索，不重建或下载补证；不使用固定短片时长代替判断。新增外部模型实验另行确定具体样本与调用范围。

### 每周反馈

用户于 2026-10-07 选择每周日北京时间 20:00 复盘，当时创建应用侧 heartbeat「虚拟主播切片每周复盘」。它不是录制器或上传消费者功能；本次未读取应用自动化状态，不声明当前 ACTIVE。

采集入口与目录见 [维护说明](../usage/README.md#投稿反馈采集)。以 BV 号比较播放、点赞、投币、收藏、分享、评论和弹幕增量，区分新发布与已积累至少 7 天的稿件；优先比较同主播、相近发布年龄和内容类型，并结合字幕、候选依据和人工反馈。7 天是观察分组，不是删除或判坏门槛。

接口没有提供完播率、观看时长、曝光或收入；未知保持未知。每轮优先一个有样本支持的问题，报告写入 `artifacts/research/weekly-reviews/`，不把统计数据伪装成人工正负样本。

### 实施边界

长期收益目标不自动开启无人审核发布或自动分析。每次区分代码实现、离线回归、在线只读与真实模型/投稿证据；模型指导、阈值、投稿策略和主播档案先形成待应用建议。

既定周复盘只允许修复有证据且不改变生产策略的确定性小缺陷并验证；不自动投稿、报名、修改历史稿件、部署、提交或推送 Git。没有新增可靠结论时保持安静，有重要经验、已验证改进、失败或需要用户操作时通知。

## MiMo 后续优化方向

记录日期：2026-10-10。以下四项由用户提出，作为待研究方向；记录不代表已启用、已验证收益或已确定实施顺序。

当前基线：视频判断与字幕轻校正使用 `mimo-v2.6-flash`，显式关闭思考模式并限制 `max_completion_tokens=2048`；ASR 使用本地 faster-whisper large-v3；判断使用实时 API。本机实际配置由 `.secrets/runtime.toml` 覆盖仓库默认值。

### 1. 模型的思考强度

比较关闭与开启思考对选段完整性、拖尾、误判、结构化输出的影响，同时记录延迟、tokens 与费用。开启思考时需要重新评估当前 2048 tokens 的预算。

先核对接口实际支持的控制粒度。Chat Completions 提供 `thinking.type` 开关；Responses 文档说明 `reasoning.effort=none` 关闭思考，其他档位目前均开启思考且行为相同，尚不区分强度。未来若支持独立强度档位再评估接入，不能把档位名称当成已生效的能力。

参考：[Chat Completions](https://mimo.mi.com/docs/zh-CN/api/chat/openai-api)、[Responses](https://mimo.mi.com/docs/zh-CN/api/chat/responses)。

### 2. 使用 MiMo ASR

评估 `mimo-v2.5-asr` 对直播口语、专名、方言、背景音乐和多人说话的识别效果，与现有 large-v3 使用同一批人工核对样本比较。重点确认字幕需要的时间戳粒度与精度、长音频限制、上传耗时及费用，验证能接入现有时间对齐与人工编辑流程，再决定替换或作为可选入口。

ASR 是独立模型，不能因语言模型升级而推断其名称也升级。官方当前列出 `mimo-v2.5-asr`，国内价格为 0.5 元/小时；实施前重新核对接口与价格。

参考：[定价](https://mimo.mi.com/docs/zh-CN/price/pay-as-you-go)。

### 3. 优化提示词

围绕选段主题与标题一致、完整事件起止、谢礼/无关拖尾、弹幕与辅助 ASR 的时间关系，以及主播专名和上下文优化。视频选段与字幕校正分别评估，一次改变一项，保存提示词版本与原始响应；比较人工接受率、边界偏差、误删/漏选和校正准确率。保留人工审核、严格 JSON 校验与明确 drop 才允许删除的规则。

现有问题与证据见 [切片质量改进记录](../history/clip-quality-improvements-20261007.md)。

### 4. 使用批量推理

评估非实时录播分析、积压任务和离线提示词评测是否适合 Batch API。官方支持 `mimo-v2.6-flash` 与 `mimo-v2.6-pro`，价格为实时 API 的 50%；文档说明任务调度在夜间 1:00–8:00，实施时确认完成时限及实际规则。

先验证项目的视频输入方式、文件大小和多模态参数是否适用批量接口，再考虑接入。核验请求与候选的关联、提交/结果状态、失败和取消行为、结果落库及人工审核；手动即时重评和字幕编辑需单独评估等待成本。批量推理不同于当前实时请求并发设置。

参考：[Batch API](https://mimo.mi.com/docs/zh-CN/quick-start/usage-guide/text-generation/batch-api)。

### 验证与实施边界

使用同一组代表性素材和人工核对标准，记录质量、耗时与费用；区分模拟回归和真实模型效果。实施顺序尚未确定，由实验结果与用户判断决定后续取舍。本次只记录方向，不启动批量任务或额外模型调用。
